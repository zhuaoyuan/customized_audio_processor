# 500 小时运行评估（P8-T2）

> 本文所有数字都来自本机 **6 文件真实产物**（`out/<job_id>/report.json` × 6）与 P3/P4/P5 已验收基线，
> 不是调研阶段的 PoC / 计划估值。结论先行：
>
> - **全链路 RTF = 0.1282**（4431.48 s / 34,563.25 s），**500 h 音频 ≈ 64.1 h**（300 文件 × 100 min，单进程、ASR 8 线程）；
>   冷启动（analyze 未命中缓存）≈ **69 h**。
> - 与 DoD「总耗时 ≤30 h」的差距：**实测 64.1 h，超目标约 2.1 倍**（30 h 对应 RTF≈0.06，本机达不到）。
>   本文如实记录差距，并给出优化选项与重订建议，**不改数字凑目标**（§7）。
> - 磁盘：交付产物 **≈21.4 GiB ≈23.0 GB（十进制）**，≤30 GB 达标；但 `work/cache` 的 16k wav 若全量保留，
>   500 h 会到 **≈107 GiB（115 GB）**，必须按任务清理（§4）。
> - 电费 ≈ **12.8 kWh ≈ ¥7.7**（0.6 元/kWh 假设）；纠错无 key 时 **¥0**，有 key **P9 复测 ≈¥0.379/文件
>   → 300 文件 ≈¥114**（P5 估算 ¥33.6 偏低 3.4 倍；真实纠错经 P9 修复后可用，f24 202 edits，§6）。

### 1.3 数据来源与计算口径

- **耗时**：`out/<job_id>/report.json` 的 `timing`（`decode_s/analyze_s/denoise_s/trim_s/render_s/encode_s/measure_s/total_s/asr_s/diarize_s/correct_s/export_text_s`）。
  其中 `render_s` 是响度施加/迭代本身的耗时；**`total_s` 是 decode→analyze→denoise→trim→loudness→encode→measure 的整条 render 链**（含未单列的写盘/重采样/日志开销），两者不可相加。
  2026-10-24 起：`timing` 增加 `write_s`；回读子耗时进 `report.measure`（ebur128/peak/asl）；
  并去掉了旧版在 `tmp_m4a.replace()` 后对最终 `clean.m4a` 的第二次回读（该次未计时，本机外置盘上约 68 s）。
- **RTF 定义**：阶段/全链耗时 ÷ **输入音频时长**（34,563.25 s）。ASR 额外给一列 ÷ clean 时长（32,082.15 s）的口径，便于和 P4 对比。
- **缓存口径**：6 文件聚合时 decode/analyze 走本地缓存（analyze 合计仅 1.21 s：5/6 文件 0.0 s，f05 共 1.21 s）。
  冷启动变体用 P6 实测的 f24 analyze 未命中耗时（47.89 s / 4,673.29 s = RTF 0.0102）补算（§3）。
- **不含项**：首次模型下载/安装、SenseVoice 首次加载与 warm-up（约 2 s 量级）、Web UI 人工操作、失败重试。
- **质量证据**：`work/measure_f24.json` 时间戳精度基线——段起点 abs median **0.18 s** / P90 **0.47 s**，
  段终点 0.26 / 0.59 s（阈值 0.5 / 1.5 s，**达标**；PoC 对照 0.21 / 0.654 s）。

## 2. 分阶段 RTF 表（6 文件实测聚合）

| 阶段 | 6 文件合计 s | RTF(输入) | 备注 |
|---|---:|---:|---|
| decode | 20.33 | 0.00059 | 真实解码各次（含 stco 修复判断），缓存命中也记录耗时 |
| analyze | 1.21 | 0.00004 | **几乎全是缓存命中**（5/6 文件 0.0 s，f05 合计 1.21 s）；冷启动见 §3（f24 实测 47.89 s → RTF 0.0102） |
| denoise | 112.25 | 0.00325 | afftdn 44.1k |
| trim | 19.27 | 0.00056 | clean 轴映射 + 裁剪写盘 |

| encode（44.1k AAC 96k） | 458.01 | 0.01325 | 每轮闭环都重新编码 |
| measure（ebur128/闭环） | 209.72 | 0.00607 | LUFS/TP 回读与 ASL 偏差判定 |
| **render 全链 `total_s`** | **2,646.21** | **0.07656** | 分项之和 2,488.85 s；差额 **157.4 s** 为未单列写盘/重采样/日志等（每文件 12.9–40.5 s） |
| asr | 1,784.79 | 0.05164（对 clean 0.05563） | P4 真实分段 ASR，SenseVoice int8 8 线程 |
| diarize | 0.06 | ≈0 | `diar.mode=none`，无 key 降级 |
| correct | 0.18 | ≈0 | 无 `DEEPSEEK_API_KEY`，`enabled=false` |
| export_text | 0.24 | ≈0 | md/srt/txt |
| **全链合计** | **4,431.48** | **0.1282** | render 全链 + asr + diarize/correct/export_text |

要点：

- **render 全链（0.0766）比 ASR（0.0516）还贵**：它是响度/限幅闭环——每遍「渲染 → 编码 → 回读真峰值/LUFS → 偏差超限再渲」，
  6 文件实测每文件 2–3 遍（P3 记录 f24 2 遍、f20 3 遍、f05 收敛后 3 遍）。
- **ASR 是第二大项**（占全链 40%）：本机分段 ASR RTF 0.0516，明显高于 PoC 整段口径的 0.026
  （P4 已记录原因：1175 段级短段多，每段 stream 创建/解码固定开销占比高）。
- **ASR 0.0516（对 clean 0.0556）是 P4 验收口径，含 measure/whisper/diar 并发负载，偏保守**；
  P8 独占 rerun 抽样 ASR RTF 0.0232（见 §8.5）。本文主口径**不因此改动**，仍用保守值推算。
- decode/analyze 在批量场景基本免费（缓存），但**冷启动 analyze 是唯一会显著抬升 RTF 的缓存项**。
- 时间戳精度基线（`work/measure_f24.json`）作为质量证据：0.18/0.47 s ≤ 0.5/1.5 s 阈值，达标。

## 3. 500 小时推算

### 3.1 主口径（缓存已热、单进程、无并发）

- 规模：**300 文件 × 100 min = 500 h = 1,800,000 s**。
- 全链 RTF **0.1282** → 1,800,000 s × 0.1282 = **230,760 s ≈ 64.1 h**。
- 单文件口径：100 min × 0.1282 ≈ **12.8 min/文件**（DoD「单文件 ≤15 min」**达标**；总量不达标）。
- 区间（±15%，覆盖文件构成、裁剪比例、ASR 波动）：**54.5–73.7 h**。

| 阶段 | RTF | 500 h 耗时 |
|---|---:|---:|
| decode | 0.00059 | 0.30 h（≈18 min） |
| analyze（缓存命中） | 0.00004 | 0.02 h（≈1 min） |
| denoise | 0.00325 | 1.63 h |
| trim | 0.00056 | 0.28 h |
| render（响度施加/迭代） | 0.04826 | 24.13 h |
| encode | 0.01325 | 6.63 h |
| measure | 0.00607 | 3.04 h |
| **render 全链小计** | **0.07656** | **38.28 h** |
| asr | 0.05164 | 25.82 h |
| diarize / correct / export_text | ≈0 | < 0.01 h（≈25 s） |
| **合计** | **0.1282** | **64.1 h** |

> 按连续跑折算约 2.7 天；按「每晚 8 h」夜间批处理约 8 个晚上。

> **两口径说明**：ASR 0.0516/0.0556 来自 P4 验收（含并发负载，保守）；P8 `--rerun --limit 2` **独占跑**实测
> ASR RTF 0.0232（对 clean）、全链 RTF 0.1147（见 §8.5）。按该抽样全链直接外推 500 h ≈ **57.4 h**
> （2 文件样本、独占跑，仍 >30 h）。本文主口径仍用 P4 保守值 **64.1 h**，不因单次抽样调低。

### 3.2 冷启动变体

首次批处理或缓存被清后，analyze 会真实重算：

- 冷启动 RTF ≈ 0.1282 + 0.0102（P6 实测 f24：47.89 s / 4,673.29 s）= **≈0.138**；
- 500 h → **≈69 h**（比热缓存多约 5 h）。

结论：**保留 16k wav + `<id>.analyze.json` 缓存是省时关键**（P6 决策：成功后只删 clean16k，保留 16k/analyze/decode）。
若为省磁盘把 16k wav 或 analyze.json 一起删掉，analyze 缓存校验（wav 路径 + 字节数）会失败，
每批要多付 ≈5 h（500 h 规模，按 f24 冷启动 47.89 s/文件折算）。

### 3.3 与 DoD 的对照

| 指标 | DoD | 实测 | 判定 |
|---|---|---|---|
| 500 h 总耗时 | ≤30 h | **64.1 h**（±15%：54.5–73.7 h） | ❌ 超约 2.1 倍 |
| 单文件 100 min | ≤15 min | **12.8 min** | ✅ |
| 磁盘（交付产物） | ≤30 GB | **≈23.0 GB** | ✅（见 §4） |
| 时间戳精度 | median ≤0.5 s / P90 ≤1.5 s | 0.18 / 0.47 s | ✅ |

## 4. 磁盘评估

### 4.1 交付产物（8 件/文件）

clean.m4a 实测（44.1 kHz / mono / AAC 96k）：

| key | clean.m4a MiB | 每 clean 小时 MiB/h |
|---|---:|---:|
| f00 | 32.23 | 42.3 |
| f04 | 98.26 | 43.5 |
| f05 | 73.54 | 42.7 |
| f06 | 63.33 | 42.8 |
| f20 | 69.52 | 42.6 |
| f24 | 45.04 | 42.6 |
| **合计** | **381.9** | 平均 **42.9** |

- 实测区间 **42.3–43.5 MiB/h（44.3–45.6 MB/h）**，与 P3 记录的「44.3–45.6 MB/小时」一致。
- 其余 7 件（transcript.json/.md/.srt/.txt、corrections.json、report.json、edit.json）6 文件合计 **4.81 MiB**，
  按 clean 时长折算 **≈0.54 MiB/h**。
- **500 h 推算**：
  - clean.m4a：**≈21.1–21.8 GiB**（≈22.7–23.4 GB；按 500 h 输入 × 实测每小时体积、并留 2–3% 余量向上取；
    纯按 clean 时长直接外推为 ≈20.7–21.2 GiB，规划取上界）；
  - 文本：0.54 MiB/h × 500 h = 270 MiB ≈ **0.26 GiB**；
  - **合计 ≈21.4 GiB ≈ 23.0 GB（十进制）**（若 clean 取上界则合计 ≈22.1 GiB ≈23.7 GB）；
  - 距 30 GB 上限留 **约 7 GB（≈23%）** 余量 → **达标 ✅**。
- 单文件平均 ≈73 MiB/100 min（clean 71 MiB + 文本约 1 MiB）。

### 4.2 缓存真实现状（本轮新发现，必须写清）

`work/cache` 当前 **4,854 MiB**、30 个条目（13 个 wav + 12 个 analyze/decode JSON + 5 个杂项）：

| 缓存 | 数量 | 体积 | 说明 |
|---|---:|---:|---|
| `<id>.16k.wav` | 6 | 2,109.6 MiB | 16 kHz/mono/**float32**，分析/ASR 复用 |
| `<id>.clean16k.wav` | 6 | 1,958.2 MiB | clean 轴 16k，P4 ASR 用；P6 策略「成功后删」 |
| `<id>.44k.wav` | 1 | 786.2 MiB | f24 的 44.1k 残留（P3 遗留，正常流程由 render_job 清理） |

- 16k wav 码率：16,000 Hz × 4 B = **64 kB/s = 230.4 MB/h = 219.7 MiB/h**；
  6 个 16k wav 合计 2,109.6 MiB / 9.601 h 输入 = **219.7 MiB/h**（实测与理论一致）。clean16k 同样量级
  （1,958.2 MiB / 8.912 h clean ≈ 219.7 MiB/h）。
- **若 500 h 的 16k wav 全量保留：500 × 230.4 MB ≈ 115.2 GB ≈ 107 GiB**（clean16k 再一份则翻倍），
  叠加交付产物后 **≈129 GiB / 138 GB，远超 30 GB ❌**。
- 因此 **「≤30 GB」指的是导出产物（8 件），不是工作缓存**；缓存必须按任务清理。

### 4.3 清理策略（可执行）

1. **跑完即删 16k / clean16k wav，只留 `analyze.json` + `decode.json`**：
   - 每文件 JSON 约 0.1 MB → 300 文件 ≈ **30 MB**；
   - 注意：**删掉 16k wav 会让 analyze 缓存失效**（缓存校验 wav 路径 + 字节数），下次同 job 重跑要重新
     decode（3–5 s/文件）+ analyze（≈48 s/文件，P6 f24 冷启动实测）。对「一次性跑完归档」无影响；
   - 因此需要频繁重跑/续跑的队列，应保留 16k（见策略 2），**不要删 `analyze.json`**。
2. **按活跃队列保留（只在处理中保留）**：峰值 = 并发数 × 单文件缓存 ≈ 0.3–0.6 GB
   （16k 0.23 GB + clean16k 0.22 GB，100 min 文件；渲染期另有 44.1k 临时 wav ≈1.0–1.1 GB/文件，由 render_job 自清）。
   默认单进程 1 时磁盘峰值 < 2 GB。
3. **16k 转 16-bit PCM / FLAC**：float32 64 kB/s → 16-bit PCM 32 kB/s，**体积减半**；
   FLAC 视语音内容再压 10–30%，但需改缓存格式与读取代码（P9 可选项）。即使减半，全量保留仍 ≈54 GiB，仍超 30 GB，
   所以减半不能替代清理，只能降低「保留少量活跃队列 + 热缓存」的成本。

> 结论：**交付产物 ≈23.0 GB ≤30 GB 达标；缓存全量保留 ≈107 GiB 不达标，需按任务/按队列清理。**

## 5. 电费

- 假设整机功耗 **≈200 W**（i5-12400F 满载 + 主板/SSD/风扇，无独显；未用功率计实测，属工程假设）。

## 6. 纠错成本

### 6.2 P5 金标 / mock 口径估算（历史对照，偏低）

- P5 金标单块（4,200 字输入）mock 计价 **¥0.021036**；

> 以上是 mock 口径；**真实调用后已证明偏低约 3.9 倍**（见 §6.3），保留仅作历史对照。

  原因与修复见 P9（§6.4）。

## 7. 与「≤30 h」目标的差距、优化选项与重订建议

### 7.1 差距

| 项 | 值 |
|---|---|
| DoD 目标 | 500 h ≤ **30 h** |
| 本机实测 | **64.1 h**（冷启动 69 h） |
| 倍数 | **≈2.14 倍** |
| 30 h 对应 RTF | **≈0.060** |
| 本机 RTF | **0.1282**（render 全链 0.0766 + ASR 0.0516） |

差距构成（按 500 h 折算）：

- **render 全链 38.3 h（60%）**：render 24.1 + encode 6.6 + measure 3.0 + 未单列开销 4.5；
- **ASR 25.8 h（40%）**：分段 RTF 0.0516，而计划/调研的 24 h/30 h 是按 ASR RTF 0.030（PoC 整段口径）估的；
- 其余（decode/denoise/trim/diar/correct/export）合计 ≈2.2 h。

**旧口径来历**（见 `docs/实施计划.md` §9、`docs/调研报告_需求对齐版.md` §9.3）：
24 h 的估算 = ASR RTF 0.030（15 h）+ 解码/降噪/裁剪/响度 2.5–5 h + VAD 1 h 等；
DoD 30 h 在其上加余量。本机真实分段 ASR 0.0516、render 闭环 0.0766，两项都显著高于 PoC 假设。

### 7.2 优化选项与预计收益

> 收益均按 500 h 折算，且是**量级估计**；除标注外都需质量/听感回归后才可采纳，不能盲调。

| 优化项 | 机制 / 前置 | 预计收益（64.1 h →） | 风险 |
|---|---|---|---|
| ① 减少 ASL 校正 / 真峰值闭环迭代 | `loudness.measure.max_asl_iterations` 与 `limiter.max_iterations` 现为 3，实测每文件 2–3 遍；让首遍命中率更高（更准的初始 ceiling / 用上一轮 base 做 `gain_offset`，P3 已做过类似优化） | **−9 ~ −12 h**（→ 52–55 h） | 中：ASL 偏差与 TP 余量需回归（f00 TP 仅 −1.30 dBTP，余量 0.3 dB） |
| ② ASR 调优（合并短段 / 线程 / beam） | 分段 RTF 0.0516 的主要成本是每段固定开销；评估合并 <2 s 短段、`num_threads` 6/10/12、SenseVoice 档位 | **−6 ~ −8 h**（RTF 0.04→−6 h，0.035→−8 h） | 中：段表/时间戳/字数契约需回归（P4 基准 1175 段/15,524 字） |
| ③ ebur128 只测一遍 / 关 `vad.ebur128` | 配置已有开关；measure 当前 3.0 h/500 h | **−0 ~ −1.5 h**（与①合并后不重复计） | 低：只影响 LUFS 对照数据，不影响 ASL/TP 验收 |
| ④ `--jobs` 流水线化（render 与 ASR 跨 job 重叠） | 两者都 CPU-bound；P3 实测进程池并行反而**慢 22%**，本版 `--jobs` 只支持 1。只有 ASR 8/12 线程留 4 线程空余时可能重叠 | **0 ~ −6 h（乐观 10%）**，多数情况为负收益 | 高：需实测；不建议默认开启 |
| ⑤ 跳过已完成阶段 / 复用缓存 | 断点续跑与失败重试只重跑缺失阶段；decode/analyze 缓存已生效（6 文件 analyze 合计 1.21 s） | 对**首次** 500 h 为 0；只降低重跑/失败成本 | 低 |
| ⑥ 保留 analyze 缓存（避免冷启动） | 冷启动 RTF +0.0102 → 69 h；保留 analyze.json 即回到 64.1 h | **−5 h**（相对冷启动） | 低（缓存管理） |
| ⑦ 更快 CPU / SSD | CPU-bound，RTF 近似随单核性能反比；SSD 只影响 I/O 小头 | 单核性能 ×2 → **≈32–35 h**（仍难稳过 30 h）；×2.5 → ≈26–28 h | 换机成本 |
| ⑧ 降质量预设 | `preset fast` 关 V2、`nr=8`、关纠错；**不减少 ASL/TP 迭代次数**，V2 计算量也不是大头 | **< 1 h**，不建议为时间牺牲质量 | 质量 |

组合判断：

- **纯软件调优**（①+②+③）现实上界约 **64 → 48–52 h**（乐观且需多轮质量回归）；
- 要稳定 **≤30 h**，需要 **≈2–2.5 倍单核性能** + ASR RTF 降到 ≈0.035（即 RTF 0.06 量级），
  这已不是本机（i5-12400F）能覆盖的范围。

### 7.3 重订建议

1. **重订总耗时目标为 ≤72 h**（64.1 h 的 112%；冷启动 69 h 也在区间内），或「≤75 h」覆盖 ±15% 上界 73.7 h；
   同时保留「单文件 100 min ≤15 min」（实测 12.8 min，已达标）。
2. **或改为按硬件缩放的目标**：以本机 **RTF 0.1282** 为基准声明「RTF ≤0.13」；
   换到 2× 单核性能的机器再按 **RTF ≈0.06（≤30 h）** 验收，避免把旧口径的 24 h/30 h 直接当本机指标。
3. 若业务必须 30 h：给出明确的硬件/调优前提（≥2× 单核 + ASR RTF ≤0.035 + 迭代优化落地），
   并把 48–52 h 作为「纯软件优化后」的阶段目标。
4. **不建议**为了凑 30 h 修改 RTF 口径（例如只算渲染、不算 ASR，或把缓存命中当默认）；那会让评估失去意义。

## 9. 局限与未覆盖

1. **6 文件外推 300 文件**：样本都是 50–138 min 的课程录音；更长/更短、噪声更大、多人课程会改变 VAD 裁剪比例与 ASR RTF，
   故给 ±15% 区间。若批内含大量超短文件，固定开销占比上升，RTF 可能更差。
2. **RTF 方差**：f05 的 ASR 在并发负载下 RTF 0.0944（正常 0.0375–0.0624）；批量时应保证无并发。
   P8 独占 `--rerun` 抽样 ASR RTF 0.0232、全链 0.1147（§8.5），说明 P4 的 0.0556 是**保守口径**；
   主口径仍按 0.0556 推算（64.1 h），独占口径约 50–57 h，两者都 >30 h。
3. **未含**：首次环境安装、模型下载、Web UI 操作、失败重试、磁盘清理时间。
4. **电费为假设**：200 W 未用功率计实测；电价随地区/峰谷变化。
5. **真实 API 已实测（P9 修复后可用）**：2026-10-22 真实 key 跑过 f24 全量（P8 修复前 0 edits，
   P9 后 **202 edits / 164 段、0 整块回退**，¥0.379/文件）与 3 个单块；细节与剩余风险见 §6.4。
6. **缓存统计是 2026-10-22 的现场快照**：`work/cache` 里含 f24 44k 残留与 clean16k（P6 清理策略只对编排器成功路径生效），
   手工 `render`/`transcribe` 单独跑会留下更多中间文件，清理命令需按实际文件匹配。
